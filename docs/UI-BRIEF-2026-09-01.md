# Veil Arena interface brief

Date: 2026-09-01

## User outcome

A new player should understand the next action without knowing poker, agents, or blockchain terminology. An operator should be able to publish a competition, add sealed agents, lock the draw, and run it without treating the creation form as the live control room.

## Primary flows

### Player entry

The player chooses a competition, copies AGENT.md to a coding agent, imports the returned package, signs with a wallet, verifies an X account, and approves entry. The page must explain what is private and what becomes public at the point of action.

### Operator setup and control

The operator creates and publishes a competition on /arena-console. Publishing moves to /arena-console/:projectId/:seasonId, where roster registration, invitations, draw locking, match execution, and reward settlement live. The public watch page remains /arena/:projectId/:seasonId.

### Watching

The arena lobby lists real competitions. A competition room explains its status, leaderboard, rules, and match list. A match page shows a live waiting state or a verified replay without revealing private cards or strategy.

### Player profile

The profile is the player's reliable return point after an entry is approved. It shows the wallet session, the verified X identity and avatar when the provider returns one, and each persisted competition entry with its active version and sealed version history. Importing a package is a review step; wallet approval is the event that makes the entry durable.

The navigation keeps the same destinations on every non-home page: Arena, Champion, Enter, Host, Profile, and one contextual back link. A missing API origin or public project must produce a recoverable configuration message, not an empty page that looks like the player's entry disappeared.

## 2026-09-02 live room extension

The match room is the participant's private broadcast window. It should make
the contest feel like a game while remaining honest about the execution
boundary: the public table shows real schedule status and published receipts,
and does not invent cards, actions, chat, or intermediate hands. A signed-in
participant sees their own enrolled agent highlighted with its X avatar when
available. The opponent remains an alias plus commitment, with strategy and
private identity sealed. A public viewer sees the same table without the
participant-only card.

The interaction model follows the useful parts of the dev.fun poker
playground, checked at https://arena.dev.fun/poker-playground on 2026-09-02:
one central table, explicit run/replay state, match progress, and a compact
event feed. Veil keeps its own paper-and-ink language and replaces fabricated
live actions with truthful execution milestones and receipt progress.

Acceptance criteria:

- The room makes both agents visually present and the current table state
  understandable within one screen at desktop width.
- The participant's own seat is the only seat with private viewer context.
- Scheduled, running, failed, and completed states each explain what is
  happening and what the viewer can do next.
- Replay controls operate only on public hand receipts that the API has
  actually published.
- No private card, strategy, X identity, or synthetic match event is rendered
  for an opponent or public viewer.

## Design decisions

- Keep the existing paper, ink, signal-orange, hard-border, and offset-shadow card system because it is the product identity and creates a clear visual grammar.
- Keep pixel styling for small labels, marks, and status tags. Use a readable mono display face for large headings and dense action labels so the game character does not reduce comprehension.
- Put a back link in every non-home page header. Keep local links inside rooms when they help users move between a competition and a match.
- Use a visible X mark beside X verification status rather than a text-only label.
- Replace unexplained "register" language with a sentence that says registration adds a sealed package to a competition roster.
- Disabled actions retain readable contrast and explain what is missing. They should not look like broken or blurred content.

## Important states

- Loading: identify the page being opened, such as "Opening the competition room".
- Empty: state what is absent and give one useful action, such as hosting the first competition.
- Error: keep the reason and recovery action visible.
- Disabled: explain the missing package, wallet, X verification, or roster condition.
- Success: show the next destination, such as the public competition room or operator control room.

## Accessibility and responsive criteria

- All back links, buttons, tabs, and cards remain keyboard reachable with visible focus.
- Explanatory text uses readable contrast against the paper and panel surfaces.
- Controls stack without horizontal scrolling at 320px, 390px, 768px, and 1440px widths.
- Motion is secondary and respects prefers-reduced-motion.

## Rejected alternatives

- Keeping live draw control directly below the creation form was rejected because it makes publishing, roster management, and watching feel like one task.
- Replacing the visual system with a generic sans-serif dashboard was rejected because it removes the arena identity. The chosen approach changes only the readability of large display text.

## 2026-09-02 table and history decision

The match page is a private participant room, not a decorative simulation. A
participant may see their own agent seat and private hole cards only when the
server has a real, authenticated result for that participant. The opponent's
cards, strategy, and private identity remain sealed. Public viewers see the
same table structure, public commitments, and published hand outcomes without
the participant-only card data.

The current runner executes a match atomically and persists public receipts
after execution. Until a durable event/checkpoint stream exists, the interface
must use `scheduled`, `running`, `failed`, and `completed` states rather than
pretending to deal cards or stream actions. A completed match is a verified
replay; a scheduled match is a queue entry; a failed match is retained with a
recovery state. None of these records are silently removed.

History is separate from the live lobby. The lobby emphasizes open and active
competitions. Competition rooms retain their match list, while completed
seasons and replay receipts remain available from the competition and player
profile. Repeated entries for the same agent are grouped as version history in
the player's private view; the underlying entry and match records remain
immutable for auditability.

Acceptance criteria:

- A participant can distinguish their own seat from the sealed opponent at a
  glance.
- The table only renders card faces, hand progress, actions, and chat backed by
  persisted authorized data; otherwise it shows a clear sealed or waiting
  state.
- A completed match remains replayable and is not displayed as scheduled.
- Old scheduled or failed matches remain visible with their actual state and a
  useful next action; they do not pile up invisibly or get deleted as a side
  effect of viewing history.
- Profile history links back to the competition and replay without creating a
  second copy of the match.

Rejected alternative: a frontend-only animation of dealing, betting, or chat
was rejected because it would make the product appear to run a match that the
worker and database have not recorded.
